DevLens Engine · architecture notes

How DevLens turns a repository into a graph

A guided tour of the pipeline: what a node and an edge really are, how the engine decides that httpResponse() means http.ts::data, and why aliasing and re-exports are the hardest part of that decision. Written to be read top to bottom once, then used as a reference.

Package devlensio Languages JS/TS · Python · Java · Go · Rust 495 tests

0The mental model

Everything the engine produces is two flat arrays — a list of nodes and a list of edges. There is no nested tree, no database, no implicit hierarchy. Every question the product asks (who calls this?, what breaks if I change it?, which routes hit this model?) is answered from those two arrays. 

// a node — one addressable thing in the codebase
{
  "id": "src/http.ts::data",
  "name": "data",
  "type": "FUNCTION",
  "filePath": "src/http.ts",
  "startLine": 1,
  "metadata": { "params": ["body"], "calls": [] }
}

// an edge — a directed, typed relationship between two ids
{
  "from": "src/route.ts::loader",
  "to": "src/http.ts::data",
  "type": "CALLS",
  "metadata": { "calledName": "httpResponse", "resolvedName": "data" }
}

Notice what the edge metadata records: the name as written at the call site and the name of the declaration it lands on. They are different. Almost every difficult bug in this engine lives in that gap, so keep it in mind — section 7 is entirely about it.

The one invariant

An edge's to must be an id that exists in the node array. The engine never emits "dangling" edges; when it cannot resolve a name it emits nothing and leaves the raw name in metadata.calls. A missing edge is a fact about the resolver, not corruption of the graph.

1The pipeline

analyzePipeline(repoPath, isGithubRepo, options) is the only entry point consumers use (the CLI, the Cloud worker, the MCP server). It runs six stages, and the first four are delegated to a language extractor — inline for JS/TS, a subprocess for everything else.

1
Fingerprint — what is this repo? Language, framework, project type, monorepo layout. Also decides which extractor runs.
2
Parse — walk the source files and emit nodes. No edges yet; nodes only carry facts (names, params, calls as written).
3
Index — build the lookup maps. One pass, O(nodes). Every later stage reads these maps instead of re-walking the AST.
4
Detect edges — twelve detectors run in a fixed order (imports first, calls second). Each returns edges plus any nodes it had to invent.
5
Score & filter — prune floating declarations, count connections, score importance, apply thresholds.
6
Artifact — nodes, edges, scores, stats, routes, exports map, git info. This is what gets stored and rendered.

Stage 1 — routing

detectLanguage(repoPath) looks for package.json, pyproject.toml, pom.xml, go.mod, Cargo.toml. JS/TS runs inline (ts-morph in the same process); the other four spawn a native extractor and talk JSON over stdin/stdout. The routing decision matters later: the orchestrator's own edge detectors (detectEdges) only run on the inline path, so subprocess extractors must emit all of their edges themselves.

Stage 2 — parsing

For JS/TS, parseRepo() creates a ts-morph Project over every source file (skipping node_modules, build output, tests/stories as leaves) and emits one FILE node per file plus a node per function, hook, component, class, method, or store.

A crucial design choice: the parser does not resolve anything. It records facts. For a function body it records the callee text verbatim: 

// parser/extractors/functions.ts
const name = call.getExpression().getText();   // "httpResponse", "axios.get", "US.get"
…
acc.sites.push({ name, argCount, argTypes });   // one record per (name, arity, types)

That verbatim string is why imports must be resolved later, and it is the root of every aliasing question in this document.

Stage 5 — scoring, briefly

scoreAndFilter() runs pass 0 (pruneDisconnected: drop STRUCT/INTERFACE/ENUM/PACKAGE/TRAIT nodes with zero edge participation), then counts per-node connections, computes scores (type bonus × reputation × connectivity), derives FILE scores from their children, and applies the noise thresholds. It is deterministic: the same repo at the same commit yields byte-identical output.

Overload ids are generated in exactly one place

applyOverloadDisambiguation() rewrites colliding ids after parsing, using the declaration's own arity (never an ordinal, so reordering functions cannot change ids). Every later consumer that maps a declaration to an id — the exports map and the new export-binding table — goes through parser/declarationIds.ts. That is deliberate: duplicating the rule is how a table ends up pointing at file::fmt while the node is file::fmt#2.

FILE nodes are real callers

Module-level code (const app = express(), boot() at the top of main.ts) belongs to the FILE node, not to any child. Those calls produce normal CALLS edges with metadata.scope = "module". There is no separate edge type for them — the caller kind is already in from.type.

3Lookup maps

Edge detection is not allowed to walk the AST. By the time stage 4 runs, the parser's Project is gone, and callEdges.ts only receives plain JSON. So everything the detectors need is pre-indexed in buildLookupMaps() — one pass, O(nodes):

Why maps and not AST queries

Parsing a 5,000-file repo with ts-morph costs seconds; answering "is there a node called X" by scanning would cost the same for every call site. Every resolution step below is a hash lookup, which is what keeps edge detection in the tens of milliseconds.

4Edge detectors

detectEdges() runs twelve detectors in a fixed order. The order is not cosmetic: importEdges must run first because it fills the alias maps that callEdges reads.

4propEdgesPASSES_PROPcomponents

Two details that surprise people: (a) detectors may invent nodes — third-party method nodes, ghost event and route nodes — and return them alongside edges, deduped into ghostNodes; (b) a missing edge is silent by design. The engine never guesses an id it cannot justify, so "no edge" is the only failure mode.

5Scoring & pruning

The graph you see is not the graph the detectors produced — it is that graph after four passes:

  1. Prune disconnected — zero-edge type declarations are floating dots; drop them (and clean childNodeIds/resolvedCalls that referenced them). CLASS is never pruned.
  2. Count connections — per node: in-degree, out-degree, by edge type.
  3. Score — type bonus × reputation × connectivity; FILE score derived from children, so a file is as important as what it contains.
  4. Filter — noise thresholds drop the long tail; the result is deterministic.

The refilter path (refilterPipeline) reuses stored scores, so changing thresholds never re-parses the repo.

7Name resolution — the hard part

This section is the reason the rest of the document exists. Read it once slowly; the code becomes obvious afterwards.

7.1 Two name spaces

At any call site there are two different names in play:

ExampleWhere it lives
call-site namehttpResponsetext inside the caller's body → metadata.calls
declaration namedatanode.name / node.id
exported name (the bridge)httpResponseonly inside import/export statements — no node holds it

The engine's job is to walk from the first column to the second. When the two strings happen to be equal, a global name index is enough. When they differ, it is not.

7.2 Three places a rename can hide

// 1 · import alias — the caller renames
import { data as httpResponse } from "./http";

// 2 · export alias — the module renames, the caller doesn't know
export { data as httpResponse } from "./http";

// 3 · both, plus any number of hops in between
export { httpResponse as publicName } from "./index";

Before this work, only case 1 was modelled: importEdges read getImportDeclarations() and stored localAlias → importedName. Case 2 was invisible — the engine never read a single export declaration — so a name that only existed as a re-export could not be found by any amount of retrying.

The reported bug, mechanically

route.ts writes httpResponse(...). The alias table says httpResponse → httpResponse (identity — the import renamed nothing). The global name index has no node called httpResponse, because the only declaration is data. Result: 219 unresolved call sites, 0 nodes named httpResponse. Not a lookup bug — a missing table.

7.3 Modules are export surfaces

The missing idea is simple: every module has an export surface — a map from the names it exposes to the declarations those names really denote. For src/index.ts containing export { data as httpResponse } from "./http", the surface is: 

src/index.ts → { httpResponse: [ "src/http.ts::data" ] }

Note what is not in there: no intermediate alias, no second file, no chain. The surface of a module in a 20-hop chain looks exactly like this — one entry, pointing at the origin. That is the whole trick.

7.4 The binding tables

Two maps are built once, by importEdges, while the ts-morph Project is still alive:

// "where did this local name come from?"
importTargets["src/route.ts"]["httpResponse"] =
  { targetFile: "src/index.ts", importedName: "httpResponse", kind: "named" }

// "in this module, what does this exported name really denote?"
exportBindings["src/index.ts"]["httpResponse"] =
  [ "src/http.ts::data" ]
  • importTargets keeps the resolved file. The old map discarded it even though ts-morph had already computed it.
  • exportBindings is produced by sourceFile.getExportedDeclarations() — the TypeScript checker's own answer to "which declaration does this exported name denote?" — and each declaration is mapped to its node id via the shared overload-aware helper.
Why the compiler does the chain-walking

A re-export is an alias symbol: a name bound to another module's symbol, not a new declaration. The checker follows those bindings — through export *, barrels, defaults, cycles and path mappings — and hands back the origin declaration. So a 20-hop chain is one query, not twenty. We store the answer, not the walk.

reexportLinks records the individual hops (file → name → next hop). It is never consulted for resolution; it exists so the UI can explain how a name arrived, without inventing graph edges for something that is not a code relationship.

7.5 The resolution ladder

callEdges resolves each call site in three tiers, cheapest and most precise first:

1
Third-party — package alias map, unchanged. axios.get → [npm]/axios::get.
2
Module-scoped — importTargets[node.file][rootName] → exportBindings[targetFile][importedName]. Two hash lookups. Member calls (US.get()) append the suffix and require the id to exist.
3
Legacy name match — global nodesByName, then the one-hop alias substitution. Kept so repos where module resolution fails behave exactly as before.
// the whole tier-2 branch, in essence
const imp = lookup.importTargets.get(node.filePath)?.get(rootName);
if (imp) {
  const ids = lookup.exportBindings.get(imp.targetFile)?.get(imp.importedName);
  if (ids?.length) targets = ids.map(id => nodesById.get(id)).filter(Boolean);
}
// …then overload resolution picks the sibling, and the edge is emitted

Why this is strictly better than name matching, in one sentence: the module tells you which declaration, so there is nothing left to guess. Two files exporting data no longer compete — each importer resolves to its own module's export, and closestByPath is only reached for real overload groups.

7.6 Twenty hops, two lookups

Fixture: c00.ts declares realOriginal; each of c01…c20 renames and re-exports it; leaf.ts imports alias20 and calls it.

call site
alias20(41) inside src/leaf.ts::useLeaf
tier 2 · hop 1
importTargets["src/leaf.ts"]["alias20"] → { file: "src/chain/c20.ts", name: "alias20" }
tier 2 · hop 2
exportBindings["src/chain/c20.ts"]["alias20"] → ["src/chain/c00.ts::realOriginal"]
edge
useLeaf → src/chain/c00.ts::realOriginal — no scroll through c19…c01 anywhere

The provenance is still available, recorded once on the edge:

"aliasChain": [
  "src/chain/c20.ts::alias20", "src/chain/c19.ts::alias19", …,
  "src/chain/c01.ts::alias01", "src/chain/c00.ts::realOriginal"
]

The chain is presentational. It is memoised per (file, name), depth-capped and cycle-guarded, and computed only when a re-export actually happened.

7.7 What lands on the edge

No new edge type — on purpose

An alias is not a code relationship; drawing httpResponse → data as an edge would invent topology that does not exist. edge.to is already the origin, so the graph is truthful, and the alias story lives in metadata where it belongs. Consumers that want to show "why does this call land here?" read calledName + aliasChain.

7.8 Cost model

export-binding pass 6 ms / 91 files 17 ms / 558 files import scan it joins 780 ms (ts-morph module resolution) kysely e2e: import 525 → 556 ms, edges identical

The table is built inside the Project that importEdges already creates, after the import scan has warmed the checker — so the marginal cost is single-digit milliseconds. Built in a fresh Project instead, it cost ~570 ms, because a new checker has to be constructed. That measurement is why the pass lives where it does.

Per call site, resolution is O(1): one map read for the import, one for the export surface. Chain depth never enters the runtime path.

8The same problem in five languages

"Call-site name ≠ declaration name" is not a TypeScript quirk. Each language spells it differently, and each extractor solves it with its own resolver because subprocess extractors emit their own edges.

LanguageHow the rename appearsHow it is resolved
JS / TS import { a as b }, export { a as b } from, export *, default/namespace imports TypeScript checker: getExportedDeclarations() collapses the chain; importTargets + exportBindings + three-tier ladder (7.5)
Python from .http import data as httpResponse; __init__.py re-exports; from .x import * No compiler table, so _resolve_in_module() walks it: declarations → import bindings (with the original name) → star sources; cycle-guarded, depth-capped
Rust pub use inner::realOriginal as alias01; then use crate::c20::alias20; resolve_bound_name(): item in module → use binding target → glob sources. V1 has no visibility model, so every use is treated as re-exportable (a safe superset)
Go import a "example.com/x/api" — package aliases only Already handled: Alias → import path symbol maps. Go has no re-export construct — a package's identifiers are its declarations — so the chain phenomenon cannot occur
Java None. Imports bind a simple name to a type or a static member; there is no renaming and no re-export Static imports already resolve to the containing class; nothing to add
Why Python and Rust must walk the chain themselves

TypeScript has a symbol table and a checker; Python and Rust extractors only have syntax. So the "export surface" has to be built from the language's own namespace rules — Python's module namespace = its declarations plus everything it imported, Rust's module namespace = items plus use bindings. Same algorithm, different source of truth. Go and Java have no such rule to model, which is why they needed no change.

Metadata parity: JS/TS and Python emit resolvedName, aliased and aliasChain; Rust emits resolvedName + aliased (its chains are resolved, but per-hop provenance is not recorded yet). Go and Java have nothing to report.

9Multi-language transport

Non-JS extractors are separate programs. The contract is deliberately boring: 

// stdin
{ "repoPath": "/abs/path", "options": { "includeThirdPartyLibs": ["requests"] } }

// stdout — JSON only (logs go to stderr)
{ "fingerprint": {…}, "nodes": […], "edges": […], "routes": […],
  "stats": {…}, "errors": [ { "file": …, "error": … } ] }

Rules the orchestrator relies on:

  • one process per repo, deterministic output (byte-identical on repeat runs);
  • relative file paths; node ids path::name;
  • non-fatal errors go in errors[] — one broken file must not fail the run;
  • the extractor emits all edges itself, including IMPORTS and CALLS, because detectEdges() is inline-only.

10Third-party gating

External packages are opt-in. With an empty includeThirdPartyLibs the engine emits zero [npm]/[pip]/[mod]/[crate] nodes and zero third-party edges — but metadata.calls still records the names, because metadata is context, not topology.

When a package is enabled, third-party resolution runs before local resolution (tier 1): axios.get becomes [npm]/axios::get, created lazily on first sight. The alias/re-export work in section 7 sits entirely in the local path and never touches this gate — a property the alias test suite asserts explicitly.

12Debugging a missing edge

When someone reports "this call has no edge", work backwards through the four places it can break:

  1. Did the parser see the call? node.metadata.calls should contain the name. If it is empty, the call is filtered as a builtin/hook or lives outside a tracked scope.
  2. Did the import record a target? lookup.importTargets.get(caller.filePath)?.get(rootName) — if undefined, the specifier was classified third-party or did not resolve to a repo file.
  3. Does the target module export that name? lookup.exportBindings.get(targetFile)?.get(importedName) — if undefined, the name is a type, a plain value with no node, or an anonymous default.
  4. Did tier 3 also miss? Then no node with that name exists anywhere — grep the repo for the declaration.
# dump a graph for any repo, then inspect the CALLS edges
bun src/debug/exportGraph.ts /path/to/repo /tmp/graph.json
python3 - <<'EOF'
import json; g = json.load(open("/tmp/graph.json"))
print([e for e in g["edges"] if e["type"] == "CALLS"][:5])
EOF

Two frequent false alarms: an edge exists twice with different metadata (dedup is per (from, to, type), so two overload call sites can legitimately produce one edge), and a node looks missing because pruneDisconnected removed a floating type declaration.

Source of truth for behaviour is always the code: src/pipeline/index.ts (orchestration), src/parser/ (nodes, overload ids, exports map), src/graph/ (index + detectors), src/scoring/ (pruning + scores), extractors/<lang>/ (native extractors). This document explains the shape of those decisions; when they disagree, the code wins — update the document.
